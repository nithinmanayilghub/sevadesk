# Story 4.3: The Inbox lists all Conversations

## What was built
- A new column `conversations.last_message_at` (migration `0010`). Every received Message sets it with `max(old, new)`, so it never moves back.
- `PINNED = Conversation.state == literal_column("'handoff'")` in `inbox/models.py`. It is one expression, shared by the index and every query.
- An index `ix_conversations_inbox_order (business_id, pinned DESC, last_message_at DESC, id DESC)`. It serves the list order, the next page, and the count.
- `GET /api/v1/inbox/conversations?cursor=…&limit=…` returns `InboxPage {conversations, next_cursor, chat_slug, timezone}`. Needs Human chats are first, then the newest activity.
- A keyset cursor `v1.<pinned>.<microseconds>.<id>`. A bad cursor gives 422 `invalid_cursor`.
- `GET /api/v1/inbox/needs-human-count` returns `{count}`.
- Both routes are for Owner and Staff only (FR-10). They have a poll limit of 120 per member per 60 s → 429. If Redis is down → 503 (fail closed).
- Frontend:
  - `InboxList`: rows, a status badge, the time in the Business timezone, Load more, and a poll every 5 s.
  - A two-pane inbox layout from 1024px.
  - `useNeedsHumanCount`: the red number on the Inbox tab, on every app page.

## Why
- An Owner must see every chat in one place, with the urgent ones (Needs Human) on top (FR-23, FR-24).
- `last_message_at` is a copy of the newest Message's time. Without it, every list load would read all Messages to sort the chats.
- Keyset paging, not OFFSET: a new Message moves a chat to the top. OFFSET would then show one row twice. A sort key does not shift.
- `'handoff'` is fixed SQL text. With a bound parameter (`$1`), the reused "generic" plan could not use the index.

## Data flow
List: browser `InboxList` → `GET /inbox/conversations?cursor=c` → `ActorDep` (session → member + Business) → `count_inbox_poll` → `list_inbox` (Role check, parse the cursor) → `inbox_page`: ONE query, conversations JOIN the newest Message (`seq = last_seq`), `WHERE (pinned, time, id) < cursor`, `ORDER BY` all DESC, `LIMIT 21` → 20 rows + `next_cursor` → `appendPage` (Load more) or `mergePoll` (poll) → the rows on screen.
Count: `/app` layout → `useNeedsHumanCount` (only with `use_inbox_and_bookings`) → `GET /inbox/needs-human-count` → `count_needs_human` → the red pill on the Inbox tab.

## Concepts learned
1. **Denormalized column:** keep a copy of a fact where the read needs it. Every writer must keep it right (here with `max()`).
2. **Keyset pagination:** "start after the last row I saw". Use a unique tie-breaker (the id) so the page edges never split rows unpredictably.
3. **Row compare:** `(a, b, c) < (x, y, z)` compares like dictionary order. One condition says "after the cursor".
4. **limit + 1:** ask for one extra row to learn whether a next page exists.
5. **Expression index + generic plan:** an index on `(state = 'handoff')` helps only a query that says exactly that. A parameter `$1` hides the value from a reused plan.
6. **Stale answers in the browser:** stop the poll during Load more, and check `signal.aborted` before you merge. (You found this gap at the Task 5 checkpoint.)
7. **Trust boundary on input:** the cursor regex caps the time at 17 digits, so a forged cursor cannot reach past year 9999 and crash with a 500. (Your hands-on test proves this.)
