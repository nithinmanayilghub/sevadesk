# Story 4.2: The Chat Page stays live by polling

## What was built
- `GET /api/v1/chat/{chat_slug}/messages?cursor=…` now polls. The answer is `{changed, messages, snapshot, cursor}`. "No change" gives `changed: false` and no Messages.
- A version counter in Redis, `ver:<bid>:<cid>` (`core/versions.py`). It goes up only after a commit (`after_commit` listener), and it starts at a random big number.
- A cursor `v1.{bid}.{after_seq}.{version}`: the browser's bookmark of what it already has.
- A fast path: cursor + known cookie → Redis map `chat_visitor:<bid>:<token_hash>` → slug check → compare versions. A "no change" poll never touches Postgres.
- A slow path: the full read from Postgres. It also writes the Redis map, so the next poll can be fast.
- A poll limit: 600 per IP per Business per 60 s → 429 `too_many_polls`. If Redis is down → 503 (fail closed).
- Frontend: `usePoll` (one shared poll loop, every 5 s, no poll while the tab is hidden, "Reconnecting…" after 3 failures). `chatPoll.ts` merges each answer and draws one list sorted by `seq`.

## Why
- A Customer must see an agent's reply without a reload. Polling is the simplest way (AD-7). WebSockets can come later.
- Most polls find nothing new. If each one went to Postgres, many open Chat Pages would load the database for no reason. Redis answers "no change" in about 1 ms.
- The version goes up only after the commit. If it went up before, a poll could save the new version but miss the new row. Then every later poll says "no change" and the Message never shows.
- The slug check keeps tenants apart: a map entry from Business A never answers for Business B.

## Data flow
Both paths live in `inbox/chat_poll.py` (`poll_chat`); the router only passes the cookie token, cursor and IP.
Fast (no change): browser `usePoll` → `GET …?cursor=c` → parse the cursor → cookie known? → Redis map lookup + slug check → `tenant_scope(bid)` → count the poll → `read_version` reads `ver` in Redis → same → `{changed: false, cursor: c}`.
Slow (anything else): `chat_business_scope` (slug → Business in Postgres) → count the poll → read version FIRST, then Messages after `after_seq` → remember the map → `{changed: true, messages, snapshot, cursor}` → `mergePoll` adds only newer seqs → `chatItems` draws them.

## Concepts learned
1. **Version counter:** a number that goes up on each change. Compare 2 numbers instead of reading all the rows.
2. **after_commit:** run code only when the save is final and other connections can see it.
3. **The order rule (READ COMMITTED):** read the version first, then the rows. Then the cursor's version can never be newer than the rows it saw.
4. **Fast path / slow path:** answer the common case cheaply. Any doubt goes to the full, safe path.
5. **Fail closed:** if the limiter cannot count (Redis down), refuse the request. Do not let it through uncounted.
6. **One poll at a time:** a `setTimeout` chain plus an `AbortController` stops two polls from overlapping.

## Numbers (NFR-3, local Docker stack)
- 100 "no change" polls: p50 0.031 s, p95 0.066 s, max 0.25 s (goal: p95 < 0.5 s). A first run had 2 outliers of 30 s that were not in the backend logs (host disk load).
- Trace volume: each open Chat Page makes 12 poll spans per minute. Fast-path spans have no database child span.
- Chat Page first load: **199,446 B** (limit 204,800).

## Demo checks (2026-11-25, after the merge)
- Hidden tab: no polls while hidden; one catch-up poll on return. On Windows, Chrome also counts a window that another window fully covers as hidden, so the page stops polling then too.
- Grafana Cloud traces:
  - Fast poll: 5 spans (Caddy, backend, 3 × `http send`), **no `SELECT`**, about 9 ms.
  - Slow poll: 9 spans, **4 `SELECT`** (Business by slug, visitor token, Conversation, Messages) of about 41–82 ms each to Neon, plus about 250 ms to open a new Neon connection (not traced). About 524 ms in total.
- p95 loop from a laptop in India, 100 "no change" polls with `curl` (a new https connection each time): all 200; p50 0.180 s, **p95 0.238 s**, max 0.297 s (goal < 0.5 s). Most of that is the trip over the internet; the server part is about 9 ms.

## Surprises
- Frontend tests fail in WSL (`Cannot find module '@rolldown/binding-…'`): `node_modules` holds Windows binaries. Run vitest in PowerShell, or call `powershell.exe` from WSL/tmux.
- The Opus review found that a cleared cookie kept the old chat on screen, and its high `seq` hid the new chat's replies. Fix: a poll answer with no cursor resets the chat.
- With low RAM and the Docker stack running, the full vitest run flaked. `--maxWorkers=2` fixed it.
