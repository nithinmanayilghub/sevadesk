# Story 4.5: Delete a Customer and all their data

## What was built
- A new permission `manage_customer_data`, for the Owner only (`accounts/permissions.py`). Staff and Technicians get 403 before any lookup.
- `TenantRepository.delete_where` (`core/repository.py`): one DELETE statement that always adds "only this Business". No delete can reach another Business's rows.
- `inbox/service.py`:
  - `customer_details`: the data for the sheet ("Customer since", Conversations, Messages).
  - `delete_customer`, in one transaction:
    1. Lock the Customer row.
    2. Lock the visitor token rows (lock 1, like a send).
    3. Lock the Conversation rows (lock 2, like a send).
    4. Delete child-first: Messages → Conversations → visitor tokens → Customer.
    5. Mark each Conversation "changed", so open screens leave the Redis fast path.
    6. Add a trace note `customer.deleted {conversations, messages}` (counts only, no personal data).
- Two routes:
  - `GET /api/v1/inbox/conversations/{id}/customer`
  - `DELETE /api/v1/inbox/customers/{id}` (204)
- Review fix: a Customer send that waited for a token row which a delete then removed got a 500 error. Now `ensure_and_lock` makes the row again, and the browser starts as a new Customer.
- Frontend: `CustomerSheet` (shadcn Sheet + AlertDialog), opened by a "Customer" button in the Conversation header. The confirm says what goes and that it cannot be undone. After a delete, the page goes back to the Inbox.
- Hands-on (yours): a `SheetDescription`, so a screen reader hears what the sheet is for, with a test.

## Why
- NFR-8 (DPDP Act, India's personal data law): when a Customer asks, the Business must delete their data, all of it.
- AD-13: `inbox` orchestrates the delete. In Epic 5, `bookings.delete_for_customer` runs first, at the marked spot.
- One transaction: never a "half delete".

## Data flow
"Delete customer" → confirm → `DELETE /inbox/customers/{id}` → `ActorDep` → `delete_customer` → Role check (403) → lock the Customer (404 if missing or another Business's) → lock the tokens → lock the Conversations → 4 DELETEs → commit → the Redis version goes up for each Conversation → 204 → `router.push("/app/inbox")`.
The Customer's open Chat Page: next poll → the version differs → slow path → no token row for this cookie → "changed", no Messages, no snapshot. Their next send starts a new Customer.

## Concepts learned
1. **One transaction = all or nothing:** a rollback undoes every DELETE, so we never keep a half-deleted Customer.
2. **Child-first delete:** a foreign key refuses to delete a parent while a child still points at it.
3. **Lock order prevents deadlock:** the delete takes locks in the same order as a send (token → Conversation). The new test fails if the order changes.
4. **A locked read can find nothing:** under READ COMMITTED, a request that waited for a lock skips a row that was deleted meanwhile. Code must handle "the row is gone".
5. **Tell open screens:** bump the version, or the Redis fast path says "no change" forever.
6. **Role first, then lookup:** a fake id and a real id both give 403 to Staff.
7. **A test must fail without the fix:** the old lock test passed even with the lock removed. A mutation check (remove the line, run the test, and see it fail) proves that a test checks what it claims.

## Gate result
3 of 3 correct: why one transaction; the open Chat Page's poll after a delete; what breaks with the wrong lock order. No new gaps.

## Deferred (from the final review)
- Redis `ver:` and chat-map keys outlive the delete. A failed version bump leaves open screens stale until a reload.
- A poll caught mid-delete can get one 500.
- The "one visitor token = one Customer" rule has no test.
