# Story 4.4: Reply to a Customer and take over the chat

## What was built
- `inbox/service.py` has the only two functions that change a chat's state: `start_handoff` (any state → `handoff`) and `end_handoff` (only `handoff` → `agent`). A real change bumps the version and adds a trace note `conversation.state_changed {from, to}`. No change → no bump.
- `_append`: one save step shared by the Customer send and the team reply (next `seq`, `last_message_at`, version bump).
- `reply`, `take_over`, `give_back`, `poll_for_member`. Each one checks the Role first, then locks or finds the row. Another Business's id → 404.
- Four routes under `/api/v1/inbox/conversations/{conversation_id}`: `GET …/messages` (poll), `POST …/messages` (reply), `POST …/take-over`, `POST …/give-back`.
- Bug fix: `poll_conversation` re-reads the row after the version (`session.refresh`). This also fixes the Chat Page poll.
- A code guard test (`tests/unit/test_conversation_state_owner.py`). It reads the backend source and allows state writes only in the two named functions.
- Frontend:
  - `ChatBubble`, `Composer`, and `useSends` moved out of `ChatPanel`, so the Chat Page and the Inbox share them.
  - `ConversationView`: the history, the Handoff bar with one button, the one-time hint, and a poll every 5 s with a stale-poll guard.
  - The Inbox layout shows one pane on mobile (list OR chat), with "← Inbox". A bad id in the URL shows "not found".
- The team-reply label: the Business name on the Chat Page, "Team" in the Inbox. Users have no names yet, so a later story adds real names.

## Why
- FR-21/FR-24: a person must be able to step in. While a person replies, the Agent must stay quiet (Handoff).
- AD-10/AR-15: if only named functions change the state, the worker (Epic 6) and the screens cannot each invent their own rules.
- AD-7: the Inbox uses the same poll shape and the same version counter as the Chat Page. One reply wakes both screens.

## Data flow
Reply: Composer → `useSends` → `POST /inbox/conversations/{id}/messages` → `ActorDep` → `reply` → Role check → `lock` (`SELECT … FOR UPDATE`) → retry check (`client_message_id`) → `start_handoff` → `_append` (seq + 1, INSERT) → commit → Redis version + 1 → the Customer's next poll (fast path) sees a new version → slow path reads the new Message → bubble with the Business name.
Take over: bar button → `POST …/take-over` → `take_over` → lock → `start_handoff` → `{state}` → `setLocalState` → the bar flips at once; other screens catch up on their next poll.

## Concepts learned
1. **State machine with named setters:** only `start_handoff` / `end_handoff` move the state. A test reads the source code to enforce it.
2. **No change → no bump:** tell screens "something changed" only when it did.
3. **Read after the version:** a poll's data must be as new as the version it returns, or a wrong screen sticks.
4. **Version after commit:** bump the counter only after the commit, so a poll never sees a new version with old data.
5. **Stale-poll guard:** a poll asked before a click must not undo the click. Drop its state AND keep the old cursor, so the next poll asks again.
6. **Role first, then lookup:** a Technician gets 403 for any id, so real ids cannot be told apart from made-up ones. (Your hands-on test proves this.)
