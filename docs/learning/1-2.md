# Story 1.2: Health checks for the API and the worker

## What was built
Two health URLs. `GET /api/health` says if the API can reach Postgres and Valkey. `GET /api/health/worker` says if the background worker is alive.
Docker Compose now runs the worker too. It uses the health checks to start services in the right order.

## Why
A running program is not always a working program. A health check asks the program: "Can you do your job right now?" People and tools use the answer to find problems fast.

## Data flow
- Caller -> `health_router.py` -> `health.py` -> Postgres (`SELECT 1`) and Valkey (`PING`) -> JSON reply.
- Worker -> writes key `health:worker:heartbeat` to Valkey every 10 s. The key expires after 30 s.
- `/api/health/worker` only checks that this key exists.

## Concepts learned
1. Health vs readiness. "Health" means the program runs. "Readiness" means it can do real work, because its dependencies answer. In Compose, `service_healthy` waits for this. Caddy and the worker wait until the backend is healthy.
2. Heartbeat + TTL. TTL means time to live: the key deletes itself after 30 s. A live worker renews the key every 10 s. A dead worker cannot renew it. So "key missing" means "worker is gone". We need no extra code to detect that.
3. One error envelope. Every error has the same shape: `{"error": {"code", "message"}}`. The frontend needs only one way to read errors. Code raises `AppError`, and one handler builds the reply.
4. Dependency timeouts. A check that fails is fine. A check that hangs is worse: the caller waits and never gets an answer. So every check has a 2 s limit (database statement timeout, Valkey socket timeouts, connect timeout).
5. Status 503. It means "Service Unavailable". The API is up, but a part it needs is not. We return 503 with `worker_unavailable` or "Not reachable: redis".
