# Story 5.2: Create a Booking for a phone-in Customer

## What was built
- Migration `0012`: `bookings.service_id` (NOT NULL, composite FK to `services`), and `customers.name` + `customers.phone` with `UNIQUE (business_id, phone)`.
- `bookings/service.py` → `create_confirmed`: the ONE write path for a confirmed Booking. Steps: Role check → capacity lock → active Service (404) → recount (409 `slot_unavailable`) → Technician choice/check (422 / 409 `technician_busy`) → insert (price from the Service) → trace event `booking.created` (no personal data).
- `bookings/repository.py` → `take_capacity_lock`: `pg_advisory_xact_lock(1001, hashtext(business_id))`, one lock per Business.
- `inbox/service.py`: `create_phone_booking` (find or make the Customer by phone) and `create_conversation_booking` (the chat's Customer). Both take the capacity lock FIRST.
- `inbox/schemas.py`: `normalize_phone` (every way of typing one number → `+91XXXXXXXXXX`, only ASCII `[0-9]`), name rules, and plain "Pick a service." / "Pick a time." messages.
- `GET /api/v1/bookings/options`: active Services and active Technicians for the form.
- Frontend `BookingSheet.tsx`: "New booking" on the Calendar, "Book a job" in a chat. The Technician picker shows only with 2+ Technicians.
- Review fixes: plain empty-pick messages, a lock-order test for the from-chat flow, isolation checks that cannot race the clock, a race test with two different Users, no guessed timezone.
- Hands-on (yours): `test_deactivated_service_gives_404_and_saves_nothing`.

## Why
- FR-27 / UJ-2: a shop owner takes jobs by phone and from chats, not only through the Agent.
- AR-14: two people must never get the last free Slot. The lock plus the recount makes this true.
- AR-4 / AD-15: one lock order for every inbox → bookings flow, so no deadlock.

## Data flow (phone-in)
`POST /inbox/phone-bookings` → Pydantic `PhoneBookingIn` (cleans the phone; a bad one is 422) → `ActorDep` → `create_phone_booking` → `require_roles` (403) → `bookings.take_capacity_lock` → `find_by_phone` or add Customer → `bookings.create_confirmed` → recount with `_free_slots` → Technician → insert → `get_session` commits (or rolls back on any error).

## Concepts learned
1. **Advisory lock:** a lock on a number we choose, not on a row. Here the number is the Business. A second booking in the same shop waits; another shop never waits.
2. **Transaction-level lock:** `pg_advisory_xact_lock` is released at commit or rollback by Postgres itself, so it can never get stuck.
3. **Lock, then recount:** the check that the time is free must run AFTER the lock. A check before the lock can be out of date a moment later.
4. **One source of truth:** the recount uses the same `_free_slots` as the Slot list. A time the page does not show can never be booked.
5. **Lock key = the shared thing:** Technicians are shared by all Services, so the key is the Business, not the Service.
6. **Lock order:** every inbox → bookings flow takes the capacity lock first. Two flows can never take the same locks in opposite orders.
7. **Rollback undoes earlier steps:** the Customer is added before the 404 for a deactivated Service; the rollback removes it too (your hands-on test).
8. **Normalize before you compare:** "98765 43210", "+91 98765-43210" and "098765 43210" become one stored form, so the unique rule works.
