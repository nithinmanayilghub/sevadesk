# Story 3.2: Set Working Hours and closed days

## What was built
- Two new tenant tables (migration 0007): `working_hours` (one row per OPEN weekday: `weekday` 0 = Monday, `start_time`, `end_time`) and `closed_days` (one row per closed date). A closed weekday has NO row.
- A new column `businesses.timezone`, default `Asia/Kolkata`, set in BOTH the model and the migration.
- Five Owner-only routes: `GET/PUT /api/v1/working-hours` (read / replace the whole week), `GET/POST /api/v1/closed-days`, `DELETE /api/v1/closed-days/{id}`. Staff and Technicians get 403.
- `hours_on(session, day)`: the front door for Epic 4 slot math. It returns that day's open hours, or `None`. A closed date wins over the weekly hours.
- `core/errors.py` now names nested fields by their dotted path (`tuesday.end_time`), so each error shows under its own day.
- `frontend/src/lib/time.ts`: "10:00 am – 6:00 pm" and "Fri, 25 Dec". Settings → Working Hours page (`/app/settings/hours`).

## Why
- Working Hours are clock times ("10:00 every Monday"), not moments, so they are stored as `time`, not `timestamptz`. The Business timezone says how to read them.
- "Today" comes from the Business clock, not the server's UTC clock. At 2:00 am on 2 Dec in India, the server still says 1 Dec.
- Save replaces the whole week: ONE `DELETE` statement, then the INSERTs. Deleting row by row fails, because SQLAlchemy sends INSERTs before DELETEs in one flush, and the new Monday clashes with the old one.
- The Business row is locked (`SELECT … FOR UPDATE`) during a save, so two saves at the same moment run one after the other.

## Data flow
Owner taps Add closed day → `POST /api/v1/closed-days {"day": "2026-12-25"}` → `ClosedDayIn.check_day` (text → `date`, or "Pick a date.") → router (session + actor) → `add_closed_day`: Role check → lock the Business row → past date? → already closed? → `ClosedDayRepository.add` (sets `business_id`, flush) → 201 → the page reloads the list → "Fri, 25 Dec".

## Concepts learned
1. Clock time vs moment: `time` for "10:00 every Monday", `timestamptz` for one exact point in history.
2. "No row" can be data: 0 rows in `working_hours` = closed every day.
3. A field validator puts its error on that field (`tuesday.end_time`); a model validator puts it on the whole object (`tuesday`).
4. `info.data` holds the fields that were already checked, in order, so `end_time` can compare with `start_time`.
5. A hand-written `WHERE business_id = …` on a DELETE must be guarded by an isolation test (`check_replace_working_hours`).
6. A row lock (`FOR UPDATE`) makes a second save wait, instead of crashing on a unique rule.

## Surprises
- A Plan review by Opus found that the first plan would fail its own tests in 3 places (error on the wrong field, INSERT-before-DELETE, missing model default). Reviewing a plan before coding is cheap.
- Input fields typed `str` that the validator turns into `time` work, but the types lie. `mode="before"` validators keep the type honest.
- The DELETE route needed `422` in its `responses`, or the frontend types showed FastAPI's default error shape.
- Chrome's device toolbar (F12, then Ctrl + Shift + M) shows the page at phone width.
