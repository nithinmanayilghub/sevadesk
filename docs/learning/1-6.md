# Story 1.6: Merge to main deploys the demo

## What was built
Every merge to `main` now puts the new version on the always-on demo server, with no hands. After a green build, the CI job `deploy` logs in to the demo server (a DigitalOcean droplet) with SSH, runs `deploy.sh`, and then checks that the public URL answers with the new commit ID.

## Why
A demo that you update by hand gets old fast, and hand steps get forgotten. An automatic deploy means `main` and the demo are always the same. The order "migrate first, then switch" means a bad migration never takes the demo down.

## Data flow
Merge PR → CI: lint → test → eval → build (images pushed to GHCR, tag = commit SHA) → deploy job: SSH into the VM, copy the demo files to `/opt/sevadesk/` → `deploy.sh <SHA>` on the VM: pull → migrate → up → prune → CI calls `https://<ip-with-dashes>.sslip.io/api/v1/hello` and checks `version == SHA`.

## Key files
| File | Level | Job |
|---|---|---|
| `infra/demo/deploy.sh` | CORE | pull → migrate (new image, one-off container) → up `--wait` → prune. Stops at the first error. |
| `.github/workflows/ci.yml` (job `deploy`) | STANDARD | Runs only on `main`, after `build`. SSH, copy files, run `deploy.sh`, check the URL. |
| `infra/demo/docker-compose.yml`, `Caddyfile`, `.env.example` | STANDARD | The demo stack: Caddy (HTTPS), backend, worker, frontend, Valkey (AOF), otel-collector. Postgres is Neon. |
| `infra/demo/README.md` | STANDARD | The one-time set-up runbook. |

## Concepts learned
1. Migrate first, then switch. If the migration fails, `up` never runs, so the old version keeps serving.
2. `set -e`. A shell script stops at the first failed command. That makes the safe order automatic.
3. Same image everywhere. CI builds one image per commit. The demo runs that exact image, tagged with the commit SHA. The worker uses the backend image with another command.
4. Proof of deploy. `/api/v1/hello` returns the commit SHA, so CI can prove that the new version is really live.
5. SSH trust, both ways. The deploy key proves to the VM that GitHub is allowed in. `known_hosts` proves to GitHub that the VM is really ours.
6. A healthcheck can cost money. A check that calls Postgres every 30 seconds keeps Neon awake all day. The demo backend check only tests that its port is open (AR-22).

## Surprises
- Oracle's free ARM VMs were "out of capacity" for days (Hyderabad has one availability domain), and Pay-As-You-Go needed a ~₹10,000 card hold that the card declined. We wrote a retry script, then gave up and rented a DigitalOcean droplet: 2 GB, $12/month, billed per hour (AR-24, 2026-11-12). The retry script was deleted; git history keeps it.
- Is 2 GB enough? We estimated first, then measured on the live server:

  | Container | Measured | Estimate |
  |---|---|---|
  | backend | 107 MB | 150–250 |
  | worker | 95 MB | 120–200 |
  | otel-collector | 41 MB | 100–200 |
  | frontend | 41 MB | 100–200 |
  | Caddy | 14 MB | 30–50 |
  | Valkey | 6 MB | 10–30 |
  | **Whole server** | **736 MB used, 1,231 MB free, swap unused** | 810–1,380 |

  Lesson: an estimate is a guess. Measure before you pay more.
- A DigitalOcean droplet starts with only `root`. Our CI logs in as `ubuntu`, so we made that user. Then the CI file needed no change.
- A check can lie: `grep -c '=$'` counted a good line, because base64 values end with `=` padding. The right check is `grep -c '^[A-Z_]*=$'` (a name, `=`, then nothing).
- GitHub environments have two sections, secrets and variables. A value in the wrong section is invisible to the CI file.
