# Story 1.5: One trace across the whole request

## What was built
One visit to `/api/v1/hello` now makes one trace: Caddy → FastAPI handler → Postgres query → worker job. You can see it as one picture in Grafana. Every backend and worker log line is JSON with a `request_id` and a `trace_id`. Phone numbers and address fields are masked before any log or span leaves the app.

## Why
When something breaks, you want to find the cause fast. A trace shows which step was slow or failed. The trace ID in each log line lets you jump from a log line to the whole trace. Masking keeps customers' private data out of our records (DPDP, India's data protection law).

## Data flow
Browser → Caddy (span 1, sends `traceparent` on) → FastAPI (span 2) → psycopg (span 3: the `SELECT`) → response sent → background task puts the job in Valkey, with `traceparent` + `request_id` in the job → worker reads the label → `trace_ping` (span 4, same trace).
All spans: app → `MaskingSpanExporter` → collector (port 4318) → local Grafana (default) or Grafana Cloud (set in `infra/compose/.env`).

## Concepts learned
1. Span and trace. A span is one timed step. A trace is the tree of spans for one request. All spans share one trace ID.
2. Context propagation. The `traceparent` text label carries the trace ID from one program to the next: in an HTTP header (Caddy → backend) or in the job (backend → worker).
3. Exporter and collector. An exporter sends spans out of the app. A collector is a relay that receives from all apps and sends to one destination. Change the destination in `.env`, not in code.
4. One masking point. Every exporter is wrapped by `MaskingSpanExporter`, and every log handler has `MaskingFilter`. No path can skip the masker.
5. Enqueue after commit. The job is sent as a background task, after the response, so after the database commit (AD-15). If Valkey is down, `/hello` still answers 200 and logs `enqueue failed`.
6. Reading a waterfall. Bar start = when the step began. Bar length = how long it took. Indentation = who called whom.

## Surprises (real bugs found)
- The SQLAlchemy tracing package does not support SQLAlchemy 2.1. It failed silently: no error, no spans. We trace the Postgres driver (psycopg) instead.
- The Caddy docs say Caddy sends spans over gRPC. Caddy 2.11 really uses HTTP. Only the live check showed this.
- `uvicorn --no-access-log` did nothing, because our own logging setup switched the access logger back on. Now `setup_logging()` turns it off on purpose.

## Known limits
- The Caddy span does not go through our masker. It holds only the method, path, and status.
- Free-text addresses inside a message are not found. Only fields named like `address` are hidden.
- Any 10–13 digit number is masked, so SAQ's millisecond timestamp shows as `[PHONE]`. Safe, but it hides a useful number.
