# Story 2.2: Log in, log out, and the app shell

## What was built
- `POST /api/v1/login`, `POST /api/v1/logout`, `GET /api/v1/me`. Sign-up now also logs the new Owner in.
- Server-side sessions: a random token in an `HttpOnly`, `Secure`, `SameSite=Lax` cookie named `__Host-sevadesk_session`. The DB keeps only the token's SHA-256 hash. Idle for 7 days → refused.
- Rate limit on log-in: 5 tries per account, 20 per IP, then a 15-minute lock (429 + `Retry-After`). Counted **first**, before the password check.
- CSRF guard: every `POST`, `PUT`, `PATCH`, `DELETE` must carry an `Origin` that matches the `Host`. Otherwise 403.
- One email rule (`accounts/emails.py`), NFKC passwords, NUL refused in emails (items deferred from 2.1).
- Frontend: `/login`, a 401 → `/login` redirect in the API client, and the `/app` shell (bottom tabs on mobile, sidebar from 1024px, items per Role).

## Why
- A session on the server can be killed at once (log-out, removed member). A JWT cannot (AD-5).
- Only the token's hash is stored, so a leaked DB backup gives no working cookies.
- Counting first stops parallel requests from all slipping past a count of 0.
- The browser writes `Origin` itself, and a page cannot fake it. So a forged request from another site always shows that site.

## Data flow
Log-in form → `POST /api/v1/login` → Origin guard (`core/origin_guard.py`) → `LoginRequest` cleans the email → `accounts/router.py` ends any old session in this browser → `accounts/service.log_in`: count the try (account + IP, Valkey) → find the user (`system_scope("login")`) → one Argon2 check (a dummy hash if no user) → wrong: 401, the try stays counted → right: clear the account count, `start_session` → commit → `Set-Cookie` → 200 `{roles}` → the frontend goes to `/app` or `/app/calendar`.
Every later request: cookie → `get_actor` → `resolve_session` → `Actor` (user, Business, Roles).

## Concepts learned
1. Server-side session. The cookie holds only a random key; the server holds the session and can delete it.
2. Cookie flags. `HttpOnly` (scripts cannot read it), `Secure` (https only), `SameSite=Lax` (not sent on other sites' POSTs), `__Host-` (no other subdomain can plant it).
3. CSRF and the `Origin` check.
4. Rate limiting with a fixed lock, and why "count first" beats a race condition.
5. User enumeration. Same message and same work (one Argon2 check) for "no such email" and "wrong password".
6. Trusted proxy header. Only the value our own proxy wrote can be trusted.

## Surprises
- Live check: after log-out, the Back button showed `/app` from Chrome's back-forward cache, with no server request. Fix: re-check `/me` on `pageshow` when `event.persisted` is true. Regression test: `layout.test.tsx`.
- A test that changes `REDIS_URL` must clear the settings cache too, not only the Redis client cache.
- AWS staging cannot log in yet: its load balancer is plain HTTP, and browsers drop `Secure` cookies there.
- The Grafana trace shows the Argon2 check as a ~300 ms gap between the `SELECT`s and the `INSERT`.
