# Story 4.1: Customer sends Messages on the Chat Page

## What was built
- A new module, `inbox`, with 4 tenant tables (migration 0009): `customers`, `visitor_tokens`, `conversations` (`state`, `last_seq`), `messages` (`seq`, `author_type`, `body`, `lang`, `client_message_id`, `actions`).
- `GET /api/v1/chat/{chat_slug}/messages`: this browser's own chat. It sets the visitor cookie, but writes no database row (AD-5).
- `POST /api/v1/chat/{chat_slug}/messages`: send one Message (`body` + `client_message_id`). It answers 201 with the saved Message.
- `ChatBusinessDep` (`business/dependencies.py`): every public chat route runs inside the slug's Business.
- A channel port (`inbox/channel.py`) and a webchat adapter (`inbox/webchat.py`): the cookie becomes a Conversation.
- Frontend: `ChatPanel` with bubbles, a live region, the DPDP notice until the first Message, "Not sent · Retry", and Enter-to-send only with a mouse. After the first Message, the Services list folds on mobile.
- Rate limits: 120 sends per IP per Business, and 30 per Conversation, per 10 minutes.

## Why
- A Customer has no login. A random cookie is the only way to "come back to the same chat". The database keeps only a hash, mixed with the Business id, so one browser cannot be linked across Businesses.
- Two locks in a fixed order (visitor row, then Conversation): a double tap on the first send makes one chat, and two writers never get the same `seq`.
- `client_message_id` makes a send idempotent: a retry after a lost answer returns the saved Message and makes no copy.
- The port keeps the save logic free of cookies, so WhatsApp later is a new adapter, not a rewrite.

## Data flow
Customer taps Send → `ChatPanel` makes `crypto.randomUUID()` → `POST /api/v1/chat/{slug}/messages` → Caddy → `ChatBusinessDep` (slug → Business → `tenant_scope`) → `SendMessageIn` checks the body (no control characters, no lone surrogates, 1–2000 characters) → IP limit → `_visitor_token` + refresh the cookie → `WebchatChannel.open_conversation` (save hash if new → lock visitor row → newest Conversation, locked, or a new one) → `receive_message` (same id saved? return it : Conversation limit → `last_seq + 1` → save) → commit → 201 `MessageOut`.

## Concepts learned
1. **Lock a row that exists.** On the first send there is no Conversation row to lock. So the code first makes sure the visitor row exists (`ON CONFLICT DO NOTHING`), then locks it.
2. **The "two people at the same door" method:** put the steps of 2 requests side by side in the worst order. Check the end result. Then see where the lock makes one request wait. A row lock lasts until the commit.
3. **Idempotent send:** the browser makes the id, and a retry sends the same id. The code checks for it, and a UNIQUE rule is the second guard.
4. **Per-Business hash:** the same token gives a different hash in each Business, so a leaked database cannot link one Customer's chats across shops.
5. **Validate text before the database:** JSON allows characters that Postgres cannot store (NUL, a lone surrogate). Refuse them with a 422, not a 500.
6. **Only retry what can work:** 429, 5xx and a lost network get "Retry". Other 4xx answers show the server's reason.
