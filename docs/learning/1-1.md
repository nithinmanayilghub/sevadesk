# Story 1.1: Hello path runs locally with one command

## What was built
A browser page that shows a "hello" card. The card gets its text from the API. The API reads it from Postgres.
The whole stack starts with one command: `docker compose up --build`.

## Why
Before real features, we prove every piece talks to the next one. Later stories add features on a path that already works.

## Data flow
Browser -> Caddy (reverse proxy) -> FastAPI -> Postgres -> back the same way.
- Caddy sends `/api/*` to the backend and everything else to the frontend.
- `hello_router.py` handles the request. It calls `app_meta.get_hello_value`, which reads the `app_meta` table.

## Concepts learned
1. One origin. The browser only talks to `http://localhost`. Caddy hides the services behind it. So we need no CORS rules.
2. The entry point owns the transaction (AD-15). The `get_session` dependency in `db.py` opens one transaction per request. It commits if the request succeeds and rolls back if it fails. Routers and services only use the session; they never commit.
   Two questions here. "Who commits?" The `get_session` dependency does. "When does it commit?" Before the response is sent, because the dependency is declared with `scope="function"` (`SessionDep` in `db.py`). Without that, the commit would run after the response. A failed commit would then be invisible to the browser. Both questions matter.
3. Generated API contract. FastAPI describes itself in OpenAPI. The frontend generates its types from that file. The two sides stay in sync once Story 1.4 adds a CI drift check. Until then, re-run the export and `npm run gen:api` by hand after you change an endpoint.

## Key files
- `backend/app/core/settings.py` - reads env vars into one settings object (BOILERPLATE)
- `backend/app/core/db.py` - database engine and the per-request session that owns the transaction (CORE)
- `backend/app/core/app_meta.py` - the `app_meta` table model (STANDARD)
- `backend/app/core/hello_router.py` - the hello endpoint (CORE)
- `backend/app/main.py` - builds the FastAPI app (STANDARD)
- `backend/migrations/versions/0001_create_app_meta.py` - creates the table (BOILERPLATE)
- `frontend/src/api/client.ts` - generated-types API client (STANDARD)

- `infra/compose/Caddyfile` and `infra/compose/docker-compose.yml` - the local stack (BOILERPLATE)

## Understanding checkpoint
At first I did not know why services must not commit (AD-15).
Example: step 1 saves a Booking. Step 2 fails.
- If each service commits, the Booking stays saved. The data is half done.
- With one transaction owned by the entry point, the failure triggers a rollback. That cancels step 1 too.
I answered correctly on the second try.

## Understanding Gate (2026-11-02, passed)
- Why one origin? The page and the API share `http://localhost`, so the browser sees one origin and CORS rules never apply. No CORS settings means fewer security mistakes (AD-6). Passed on retry.
- Data flow: HelloCard (`client.ts`) → Caddy (`/api/*`) → FastAPI router (`SessionDep` opens the transaction) → `app_meta.get_hello_value` reads Postgres → JSON reply → Caddy → HelloCard shows it. Passed on retry.
- What breaks if the hello row is missing (or doubled)? `scalar_one()` raises `NoResultFound` (or `MultipleResultsFound`), FastAPI returns 500, the transaction rolls back, and the page shows "Could not reach the backend." The unique constraint on `key` also blocks a second row. Passed after explanation.
