# Story 1.4: CI pipeline that blocks bad merges

## What was built
A robot now checks every change before it can reach `main`. The robot is a GitHub workflow in `.github/workflows/ci.yml`. If any check fails, GitHub blocks the merge.

## Why
People make mistakes, and your own computer hides some of them. A robot on a clean machine finds them early. Rules on `main` then make sure nobody skips the robot.

## How the pipeline works
The workflow has four jobs. Each job waits for the one before it (`needs:`).

`lint` -> `test` -> `eval` -> `build`

- lint: ruff (finds Python style problems and common bugs), import-linter (one rule: `app.core` may not import `app.main`, `app.worker` or `app.export_openapi`), ESLint (the same job for the frontend), and `tsc` (the TypeScript type check) after `next typegen`.
- test: backend `pytest` with a coverage gate of 80% (the first CI run showed 93.43%), the evals tests (99%), the frontend `vitest` tests, and an OpenAPI drift check.
- eval: runs `python -m evals.runner`.
- build: builds the backend image (the worker uses it too, so it is built once) and the frontend image, for `linux/amd64` and `linux/arm64`. The first run took about 10 minutes.

## Data flow
You push a branch -> `gh pr create` -> GitHub starts `ci.yml` -> lint -> test -> eval -> build -> four green checks -> `gh pr merge --merge --delete-branch` -> the push to `main` runs CI again and now also pushes the images to `ghcr.io/nithinmanayilghub/sevadesk-*`, tagged with the commit SHA.

## Concepts learned
1. CI (Continuous Integration). A robot runs your checks on every change, on a clean machine.
2. Pipeline, job, step. A pipeline is the whole run. A job is one stage. A step is one command inside a job.
3. Lint and formatter. A linter reads code and warns about problems. A formatter only changes the look of the code.
4. Import contract. A rule about which files may import which. Ours says the core code must not depend on the entry points.
5. Coverage. The share of code lines that tests run. Below 80%, the test job fails.
6. Alembic head and downgrade. A head is the newest migration. We need exactly one head. We also test that the database can go down to empty and back up.
7. OpenAPI drift. The API changed but the saved `openapi.json` and the frontend types did not. CI regenerates them and fails if `git diff` shows a change.
8. Branch protection and required check. GitHub rules on `main`. The four checks must pass, the branch must be up to date, and admins follow the same rules. A pull request (PR) is required, but it needs 0 approvals because you work alone. Force pushes are not allowed. GitHub's free plan protects only public repos, so the repo became public on 2026-11-03.
9. Safe tokens. `GITHUB_TOKEN` is the key the workflow gets. The top-level token is read-only. Only `build` can write packages, and its login and push steps run only on a push to `main`. A fork is a copy of the repo by someone else. A fork PR always gets a read-only token. We never use `pull_request_target`, because it gives that power to fork code.
10. Cancel rules. A newer PR run cancels the older one. A run on `main` is never cancelled.
11. Multi-arch image. One container image that runs on two chip types, amd64 and arm64. arm64 is built through QEMU, an emulator.

## A real bug CI caught
The first run failed: `tsc` said "Cannot find name 'LayoutProps'". Next.js makes that type inside `.next/`. Your computer had `.next/` from old builds. The clean CI machine did not. The fix: `"typecheck": "next typegen && tsc --noEmit"`. Lesson: "works on my machine" can hide a missing step. CI shows it.

## New merge flow
Story branch -> push -> `gh pr create` -> four green checks -> `gh pr merge --merge --delete-branch`. No direct push to `main`.
