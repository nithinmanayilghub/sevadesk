# Story 2.4: Role-based access

## What was built
- The FR-10 table in one place: `ALLOWED_ROLES` in `accounts/permissions.py`. Each row is one `Permission` (`manage_setup`, `use_inbox_and_bookings`, `see_own_bookings`, `see_dashboard`).
- One Role check: `require_roles(actor, permission)`. If no Role of the Actor is allowed, it raises `Forbidden` (403, code `forbidden`).
- `assigned_bookings_filter(actor)`: a Technician-only Actor gets their own membership id (the bookings module will keep only their Bookings); Owner and Staff get `None` (all Bookings).
- Other modules reach these through `accounts/service.py` (re-exports, like `clean_email`).
- `GET /me` and log-in now also return `permissions`. The app uses that list to hide nav items and to show "You don't have access to this page." for a forbidden URL.

## Why
- A Technician must not change prices or read every chat (FR-10).
- One helper, one table: every story checks Roles the same way, and a test compares the table with the PRD.
- The app gets the permission list from the backend, so the rules are never written twice and cannot drift.
- Hiding is for comfort only. The backend 403 is the real guard (AD-5).

## Data flow
Request with cookie → `get_actor` (reads the membership and its Roles, every request) → service calls `require_roles(actor, permission)` FIRST → allowed: go on / not allowed: `Forbidden` → the request's transaction rolls back → error handler → 403 `{"error": {"code": "forbidden", ...}}`.

App: `/me` → `permissions` → `layout.tsx` → `canOpen(pathname, permissions)` → page, or `<NoAccess />` inside the normal nav.

## Key files
- `backend/app/modules/accounts/permissions.py` - the FR-10 table, `require_roles`, `assigned_bookings_filter` (CORE)
- `backend/app/core/errors.py` - `Forbidden` (CORE)
- `backend/tests/unit/test_permissions.py` - every Role set × every permission (CORE)
- `backend/tests/integration/test_role_access.py` - 403 over HTTP, and it changes nothing (CORE)
- `backend/app/modules/accounts/router.py` - `_me()` builds the `/me` and log-in answer (STANDARD)
- `frontend/src/lib/access.ts`, `frontend/src/app/app/layout.tsx`, `frontend/src/components/NoAccess.tsx` - what the app shows (STANDARD)

## Concepts learned
1. Authentication vs authorization. Authentication: who are you (log-in, 401). Authorization: what may you do (Roles, 403).
2. 403 vs 404. 403 for "your Role may not do this". 404 for another Business's record (FR-11).
3. Check first. The Role check runs before any lookup, so a 403 never says whether a record exists.
4. Rollback as a safety net. An error inside the request undoes every change of that request, even one already flushed.
5. Union of Roles. A User may do an action if ANY of their Roles may.

## Surprises
- `backend/.venv` is a Linux venv, so the backend tests run through WSL: `wsl --cd "<repo>\backend" -e bash -lc "uv run pytest ..."`.
- PowerShell 5.1 `Set-Content -Encoding utf8` adds a BOM (3 hidden bytes) at the start of a file. Remove it before you commit.
