- (decision) Backend paradigm: modular monolith split by feature (e.g. accounts, business setup, inbox, agent, bookings); simple layers inside each module (router -> service -> repository); ports+adapters only at external edges (AI provider, channels, payments). Binds all backend code. Prevents: stories placing code by layer vs by feature inconsistently; adapters sprawling into non-swappable areas. Weighed: plain layered (no home for providers), full hexagonal (too heavy for beginner).
- (decision) Cross-module access: each module exposes a public service interface (its front door); other modules call only that, for reads AND writes. No module imports another module's repository/models internals or queries its tables. Each table has exactly one owning module. Synchronous direct calls; no event bus in MVP (revisit when reminders/campaigns in P4 need it). Prevents: booking rules duplicated in agent/dashboard; two writers of one table. Weighed: events (looser coupling, harder to trace for beginner).
- (decision) Tenant isolation: tenant context (business_id) is resolved once per request/job and a shared tenant-scoped base repository adds the business_id filter to every query and sets it on every insert; repositories never take business_id from callers. Source of business_id: staff/owner requests -> server-side from the authenticated user's membership, never from URL/body; public Chat Page -> from the server-side lookup of the Chat Page link slug; worker jobs -> business_id carried in the job payload and set as tenant context before any query. Tables without business_id are only explicit global tables (e.g. users, businesses). FR-11 isolation tests in CI on every PR. Postgres RLS deferred as a later second lock. Prevents: per-story hand-written filters being forgotten; client-supplied tenant ids.
- (question) Does a user belong to exactly one Business in MVP, or can one user be a member of many? (affects auth/session shape)
- (decision) Users and businesses: MVP = one Business per user. Modelled via a memberships table (user_id, business_id, role) owned by accounts; role lives on the membership, not the user; unique constraint on user_id enforces one-business-per-user. Lifting that constraint later enables multi-business without a schema rewrite. No business switcher in MVP. Resolves the open question on user/business cardinality. Prevents: business_id/role stored on users table by one story and on memberships by another.
- (decision) Auth: server-side sessions. Login creates a random opaque token stored server-side (session store owned by accounts); browser holds it in an httpOnly, Secure, SameSite=Lax cookie. Every authenticated request resolves session -> user -> membership (business_id, role). Logout and member removal delete sessions immediately. No JWT. Prevents: mixed auth schemes across stories; stale access after removal (FR-8, FR-9). Weighed: JWT (no store, but weak logout/revocation).
- (decision) Same-origin deployment: frontend and backend always served from one origin. A single front door routes /api/* to FastAPI and everything else to Next.js. Track A demo: Next.js + FastAPI + worker + reverse proxy together via docker-compose on the one Oracle Cloud Always Free server (Vercel dropped). Track B: ECS Fargate services behind one ALB with path routing, on-demand only. Postgres/Redis/observability stay on free managed tiers (Track A) and RDS/ElastiCache (Track B). Prevents: cross-site cookie problems; per-environment CORS drift. User direction: do not run frontend and backend on two separate services.

- (decision) Agent reply path: async. POST message -> API saves Customer Message, enqueues an agent-reply job (arq on Redis) carrying business_id + conversation_id, returns immediately. Worker runs the agent, saves the Agent Message. Chat Page and Inbox get new messages by polling a 'messages since <cursor>' endpoint. Polling rule: poll fast (about 1-2 s) only while a reply is pending, back off when idle, stop when the tab is hidden; poll endpoint is rate-limited (NFR-5). Agent failure/timeout -> FR-22 fallback written by worker. Prevents: AI calls inside web requests; per-screen different delivery mechanisms. SSE/WebSocket deferred.
- (decision) Agent facts via tools: the agent gets Services, Prices, Working Hours and free Slots only through tool calls (e.g. list_services, get_free_slots, create_booking_request, handoff_to_human) whose handlers call other modules' front doors. Facts are never pasted wholesale into prompts. A post-check validates the final reply: every Price/Slot mentioned must match a tool result in that turn; on failure retry or hand off. Tool schemas defined once in agent module; the AI port translates to provider format (Claude/Groq-OpenAI). Prevents: invented prices/slots (FR-16a, FR-17, FR-20); agent writing bookings directly. Weighed: facts-in-prompt (stale slots, cost).
- (decision) Double-booking guard: every write that takes or moves capacity (create Booking Request, manual booking, change Slot, confirm with Technician) runs in one transaction inside the bookings module: lock the Business row (SELECT ... FOR UPDATE), recount overlapping requested+confirmed Bookings vs active Technicians (and, on confirm/assign, check that Technician has no overlapping confirmed Booking), then write. Only bookings module front-door functions do this; agent, inbox and manual UI all call them. Slot-taken -> typed SlotUnavailable error the agent turns into new offers (FR-18). User chose option 1 only: no Postgres exclusion constraint for MVP (deferred as optional second guard). Prevents: races over the last Slot; technician double-assigned.
