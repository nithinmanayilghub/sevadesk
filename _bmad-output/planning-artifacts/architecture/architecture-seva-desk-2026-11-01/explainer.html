1. The big picture

SevaDesk has four running parts:

  • Next.js draws the screens. It holds no business rules.
  • FastAPI is the backend app. All business rules live here.
  • The worker does slow jobs in the background, such as AI replies.
  • PostgreSQL stores the data. Redis (Valkey) holds the job list and fast counters.
flowchart LR
  B[Browser] --> P[Front door: Caddy or AWS load balancer]
  P -->|/api/...| F[FastAPI]
  P -->|all other pages| N[Next.js]
  F --> DB[(PostgreSQL)]
  F -->|add job| R[(Redis / Valkey)]
  W[Worker] -->|take job| R
  W --> DB
  W --> AI[Claude or Groq]

Everything sits behind one web address. The front door sends /api/... to FastAPI and the rest to Next.js. Because of this, the login cookie works without extra setup.

Say it: "SevaDesk is a modular monolith. Next.js renders, FastAPI owns the rules, and a background worker runs slow AI work. One front door serves both, so cookies just work."

2. Feature modules

A monolith is one app that you deploy as one piece. Modular means we split its code by feature. Each feature folder is a module.

ModuleWhat it owns
coreShared tools: database, tenant filter, settings, logging, errors. No business tables.
accountsUsers, memberships with roles, sessions, invites.
businessThe business, its services and prices, working hours, chat link.
inboxCustomers, conversations, messages. The webchat channel.
agentThe AI agent: prompts, tools, daily cap. The AI provider plugs.
bookingsBookings, price quotes, free-slot math, the booking lock.
dashboardNothing. It only asks other modules.

Two rules keep modules clean:

  1. One owner per table. Only bookings touches the bookings table.
  2. Use the front door. Each module has a service.py with public functions. Other modules call only those functions. A CI check called import-linter blocks any other import.
flowchart LR
  dashboard --> bookings & inbox & business
  agent --> bookings & inbox & business
  inbox --> bookings
  inbox --> business
  bookings --> business --> accounts --> core

Arrows show who may call whom. They never loop back. bookings never calls inbox.

Say it: "Each table has one owner module. Modules only talk through a public service. I enforce the dependency direction with import-linter in CI."

3. One request, step by step

Inside a module, a request passes three layers:

flowchart LR
  A[router.py: reads the web request] --> B[service.py: applies the business rules] --> C[repository.py: reads and writes the database]
  • The router checks the input and calls the service.
  • The service holds the rules, for example "a booking needs a free slot".
  • The repository runs the database queries.

The data between modules travels as DTOs. A DTO (data transfer object) is a plain data shape. It is not a live database object.

4. Tenant isolation

A tenant is one business, such as "Sharma AC Repair". All businesses share one database. Every row has a business_id. Sharma must never see the rows of another business.

How we guarantee it:

  1. The server finds the business_id once per request. It never comes from the browser.
    • Staff: from the login session.
    • Public chat: from the chat link and visitor cookie. A visitor sees only chats made with their own cookie. Typing someone's phone number never shows that person's history.
    • Worker job: from the job data.
  2. A shared base repository in core adds WHERE business_id = ... to every query by itself. No builder writes that filter by hand, so no builder can forget it.
  3. The database is a second guard. Every link between tables uses two columns: (business_id, service_id). This is a composite foreign key. So the database itself refuses a Sharma booking that points at another business's service, even if the code has a bug.
  4. Isolation tests run in CI on every pull request. They test writes too, not only reads.
Say it: "Tenant scoping is automatic and server-derived. The client can never pick its tenant, and a base repository adds the filter to every query, and composite foreign keys stop cross-tenant links in the database. Postgres Row-Level Security is my planned second lock."

5. Login and roles

At login, the server makes a random token. It saves the token, and it gives the browser a cookie with the same token. The cookie is httpOnly, so page JavaScript cannot read it. On each request, the server looks up the token and finds the user.

Why not a JWT (a signed token that the server does not store)? A JWT is hard to cancel. With our sessions, logout or removing a team member works at once.

A person links to a business through a membership. The membership holds a set of roles: owner, staff, technician. A solo owner can be owner and technician at the same time.

A cookie goes with every request, even one that another website starts. That attack is called CSRF. So every request that changes data must carry an Origin header that names our own site. Other requests are refused.

6. Chat to booking

AI replies are slow (a few seconds). So the web request does not wait for the AI.

sequenceDiagram
  participant C as Customer browser
  participant API as FastAPI
  participant Q as Redis job list
  participant W as Worker
  participant AI as Claude
  C->>API: send "My AC is not cooling"
  API->>API: save message
  API->>Q: add job "agent_reply" (key = conversation + seq)
  API-->>C: OK (at once)
  W->>Q: take job, take the conversation lock
  W->>AI: ask for a reply (with tools), 9 s deadline
  AI-->>W: reply text
  W->>W: newer customer message? then drop my reply
  W->>API: save agent message (only if no human took over)
  loop every 1-2 seconds while waiting
    C->>API: anything new after my version?
    API-->>C: "no change" from Redis, or new messages + snapshot
  end
  • Polling means the page asks "anything new?" again and again. The gap is never more than 5 seconds while the tab is open. The page stops polling when the tab is hidden.
  • A cursor marks the last message the page has. Each message gets a counting number (seq), so no message is skipped.
  • No skipped messages. Only one AI job runs per conversation at a time, guarded by a lock in Redis. The job answers all customer messages up to its seq. Before it saves, it checks for a newer customer message. If there is one, it drops its own reply, because that reply is now stale. The newer job answers everything in one reply.
  • A deadline. One agent turn gets 9 seconds in total and at most 4 tool calls. This keeps us inside the 10-second promise (NFR-3).
  • No endless "typing...". reply_pending is computed from the messages, not stored. Every pending reply ends within 30 seconds, even if the worker crashes.
  • Cheap polls. Each change bumps a version number in Redis. If the version did not change, the poll answers "no change" and never touches Postgres. This saves money and lets the free Neon database sleep.
  • If the AI fails or runs out of time, the customer gets a fixed "the team will reply soon" message, and a human takes over.
Say it: "AI work is asynchronous. The API saves the message and queues a job. The worker calls the model. The client polls one snapshot endpoint. One job runs per conversation, and a stale reply is dropped, so no message is skipped or answered twice."

7. No invented prices

An AI model can make up facts. So the agent gets facts only through tools. A tool is a function that our code runs when the model asks for it.

  • list_services, get_free_slots: read real data.
  • quote_price: the server records the price as a quote. The page shows it as an "Accept ₹X" button.
  • The customer accepts only by tapping that button. The server records the tap. The model cannot say "the customer accepted", so a trick message like "ignore your rules, I accept" does nothing.
  • create_booking_request(quote_id, slot): it refuses a quote that is not accepted or has expired. The price comes from the saved quote. The model never sends an amount.

Prices and slots appear only in buttons and cards that the server builds from tool results. The reply text itself must contain no amounts and no times. A check enforces this before a reply goes out. That is simple to test, also for Hindi text. If the check fails, the agent rewrites the text once (it does not run the tools again), then hands off to a human.

Say it: "The model never supplies money or accepts on the customer's behalf. Prices live in server-built chips from a recorded quote, the customer accepts by tapping, and a post-check blocks any amount in the free text."

8. No double booking

Two technicians mean at most two jobs at 10 AM. If two customers take the last slot at the same moment, both checks can pass. This is a race condition.

sequenceDiagram
  participant A as Customer A
  participant B as Customer B
  participant BK as bookings module
  participant DB as PostgreSQL
  A->>BK: book 10 AM
  BK->>DB: take lock for this business
  B->>BK: book 10 AM
  BK->>DB: try lock (waits)
  BK->>DB: count = 1 of 2, insert, commit (lock released)
  BK->>DB: lock taken for B
  BK->>DB: count = 2 of 2, no space
  BK-->>B: SlotUnavailable, so offer other slots

The lock is a Postgres advisory lock. It is a named "wait your turn" sign, here named by the business_id. Each state change also says WHERE state = 'requested'. So two actions cannot both change the same booking.

  • One quote can make at most one booking (UNIQUE(quote_id)). A repeated call cannot double-book.
  • No slot hoarding. A bot could open many chats and hold every slot. So each conversation may have only one open request, and each visitor and IP only a few.
  • "Expired" is computed when we read: requested and past expires_at means expired. One function holds this rule. An hourly job writes it down later. So a read never has to write.
Say it: "All capacity writes go through one bookings function. It takes a per-business advisory lock, recounts, then writes. State changes are guarded updates."

9. Who owns a transaction

A transaction is a group of database writes that all succeed or all fail. The rule:

  • The entry point (the web route, the job, or the script) opens and commits it. Services never commit.
  • No AI call and no job queueing while a transaction is open. We queue the job after the commit, so the worker always finds the data.
  • The agent job is special. It calls the AI several times, so it cannot keep one transaction open. It uses one short transaction per tool call. Each write tool is idempotent: calling it twice has the same effect as calling it once.
  • Locks are always taken in the same order: the booking lock first. When inbox needs bookings, it calls bookings before it writes its own rows. Two flows that take locks in different orders can wait for each other forever. That is a deadlock.
What breaks without it: a lock stays held for 8 seconds during an AI call, and every other booking for that business waits.

10. Where it runs

flowchart TB
  subgraph demo[Demo: always on, about $0]
    O[Oracle Cloud free server: Caddy + Next.js + FastAPI + worker + Valkey]
    O --> NE[(Neon free Postgres)]
  end
  subgraph aws[AWS staging: on demand, then destroy]
    ALB[Load balancer] --> ECS[Fargate: Next.js, FastAPI, worker]
    ECS --> RDS[(RDS Postgres)]
    ECS --> EC[(ElastiCache)]
  end
  GH[GitHub Actions] -->|same images| demo
  GH -->|after manual approval| aws
  • The same Docker images run everywhere. Only the settings (environment variables) change.
  • The images are built for two chip types (amd64 and arm64), because the Oracle server uses ARM chips.
  • Pipeline: lint, tests, evals, build, deploy demo, then manual approval for AWS.
  • Neon sits in the region closest to the Oracle server, so each database call is short. Valkey saves its data to disk (AOF), so queued jobs survive a restart.
  • AWS runs for a few hours only, then terraform destroy. Always-on AWS would cost about $100–130 a month.

12. Interview practice

Q: Why a modular monolith and not microservices?
A: One builder, small scale, $10 budget. A monolith is one deploy and one database. Modules with front doors give clear boundaries. A module can split out later if it needs to.
Q: How do you stop one business seeing another's data?
A: The server derives the tenant, a base repository adds the filter to every query, and CI runs isolation tests on every PR.
Q: Why does the AI run in a worker?
A: AI calls take seconds and can fail. The worker keeps web requests fast and handles timeouts with a human handoff.
Q: How do you prevent double booking?
A: One write path, a per-business advisory lock, a recount, then a guarded insert or update.
Q: How do you stop the AI from inventing prices?
A: Tools for every fact, a server-recorded price quote shown as a button, acceptance only by the customer's tap, and a post-check that blocks amounts in free text. Evals test it in CI.
Q: A customer sends two messages one second apart. What happens?
A: Each message queues a job keyed by its seq. A Redis lock lets one job run at a time. The first job sees a newer message before saving, so it drops its stale reply. The second job answers both messages in one reply.
Q: What would you change at 100x scale?
A: Push instead of polling (SSE), Postgres Row-Level Security as a second lock, maybe an event bus between modules, and more worker processes.
